# 经验总结

## 2026-11-03 - 「后加载覆盖全局函数」的项目里，改错文件的概率极高

### 场景
`futures.js` 定义了下单/平仓/资金费，但运行时生效的是 `market/model.js` 与 `trading/contracts.js` 的覆盖版本。

### 经验
当一个函数在多个文件里被重新赋值时，源码阅读顺序不等于执行顺序；必须按 `bootstrap.js` 的加载顺序追踪，或直接看 `window` 上最终的值。

### 下次建议
修改前先 grep `函数名\s*=` 找到所有赋值点，确认最后一个加载的是谁；长期应把状态机收敛到单一实现。

## 2026-11-03 - 双写同一份状态一定会分叉

### 场景
高级委托的内存数组与 localStorage 各有一套读写路径。

### 经验
只要存在两个写入方，就一定会出现「A 删除、B 回写」的复活；退款这类不可逆操作尤其危险。

### 下次建议
一个数据只允许一个写入入口，持久化只做镜像；对「退款/扣款」操作加幂等键或状态校验。

## 2026-11-03 - 启动器的「模块已加载」不等于「模块已就绪」

### 场景
`bootstrap.js` 以 `script.onload` 判定模块成功，但模块的导出要等异步初始化。

### 经验
后置校验必须检查模块真正需要暴露的 API，而不是脚本是否执行完毕；异步初始化的模块应有就绪事件或轮询上限。

### 下次建议
为每个模块声明 `provides`，启动器统一断言；等待逻辑必须带超时与错误上报。

## 2026-11-03 - 严格模式下「覆盖全局函数」的前提是先有声明

### 场景
删除看似被覆盖的死函数后，所有 `x=function(){}` 的覆盖赋值全部抛 `ReferenceError`。

### 经验
在非模块脚本里，`function foo(){}` 会创建 `window.foo`；严格模式 IIFE 里的 `foo=...` 依赖这个已有绑定。判断「死代码」时，要同时找**赋值点**和**声明点**：声明可能是运行时必需的，即使它的实现永远不会被调用。

### 下次建议
对这类补丁链项目，删代码前先 grep `name\s*=` 与 `name(`；保留声明、把实现替换为抛错 stub，比直接删除更安全也更有表达力。

## 2026-11-03 - 同一个指标只能有一个口径

### 场景
「已实现盈亏」在合约里是毛额、现货里是净额，统计页又统一减一次手续费，导致现货被扣两次、合约看似正确。

### 经验
只要同一个数字有多个来源/多种含义，最终一定对不上；先定义恒等式（钱包变化 = 已实现 + 未实现 + 资金费），再让所有写入方遵守它。

### 下次建议
把手续费定义为「展示用聚合」，盈亏定义为「净额」；用一条守恒断言测试兜住，而不是逐处打补丁。

## 2026-11-03 - 先抽纯函数，才写得出单测

### 场景
交易计算和 DOM/全局状态缠在一起，`closePosition` 既算钱又改 DOM、写 localStorage，无法在 Node 里直接测。

### 经验
把「算」和「写」分开：纯函数只接收数字、返回数字；调用方负责扣款、渲染和持久化。抽离过程本身就能暴露边界（notional<1、200X、cushion 上限）。

### 下次建议
新增资金相关逻辑时，先写 domain 函数和用例，再接到 UI；不要反过来。

## 2026-11-03 - 「没改也保存」会摧毁一切并发保护

### 场景
行情每来一笔都无条件 `saveState()`，两个标签页互相覆盖；加修订号后，空闲保存又让另一个标签页不断被判定为「落后」而重载。

### 经验
冲突检测的前提是「保存 = 真的改了」。定时器/心跳/渲染路径不能顺手落盘，否则修订号失去语义。

### 下次建议
持久化只挂在 mutation 上；周期任务只维护内存状态，必要时用脏标记合并写入。

## 2026-11-04 - 纯前端也不能存明文口令

### 场景
`greedbit_users` 直接存 `password`，管理页口令 `123456` 写在前端，`isAdmin` 放在可编辑的会话 JSON 里。

### 经验
本地演示不等于可以省掉基本卫生：明文口令一旦随浏览器同步/截图/导出流出就是真实泄露；权限字段只要可写就等于没有权限。

### 下次建议
口令一律加盐哈希（哪怕只是 SHA-256 多轮）；管理/调试能力用构建期或 URL 开关，不要用口令；迁移旧记录时在成功登录后顺手清理。
